1. 缓存为什么快
加载一个页面时，缓存的作用是避免重复传输：

缓存命中：浏览器直接从本地（内存/磁盘）或 CDN 边缘节点读取，接近零延迟，这就是"秒开"
缓存未命中：必须回源服务器重新下载，耗时取决于服务器响应速度和网络
所以缓存的价值体现在第二次及以后的访问。首次访问无论怎么设缓存都要完整下载，这部分帮不上忙。

2. "短缓存"的问题在哪
如果所有资源都设成很短的缓存（比如几分钟）：

影响	说明
每次访问都重新下载	页面加载变慢，尤其弱网和移动端
服务器压力成倍增加	所有用户频繁回源，带宽和 CPU 开销大
用户体验不稳定	同样一个页面，有时秒开有时等好几秒
3. 推荐做法：按资源类型分级缓存
"不留缓存、及时清理"和"缓存性能好"其实不冲突，关键是用对策略：

① HTML 页面 —— 不缓存或短缓存

设置 Cache-Control: no-cache（配合 ETag/Last-Modified 做协商缓存）
效果：每次访问都回源"校验"一次，但内容没变时只返回 304，几乎不花流量，内容永远是最新的
② CSS / JS —— 长缓存 + 文件名指纹

构建时给文件名加内容哈希，如 app.8f3d2c1a.js
设置 Cache-Control: max-age=31536000（一年）
效果：内容一变，文件名就变，浏览器自动请求新文件；没变的文件继续命中缓存。既"及时更新"又"长期加速"，这是最经典的方案
③ 图片 / 视频等静态资源 —— 中长缓存

如 30 天，配合版本路径；不常变的资源没必要频繁重下
④ 接口数据 —— 按业务分

变化快的（购物车、实时数据）：短缓存或不缓存
变化慢的（配置、分类列表）：可加 5–10 分钟缓存，显著降低后端压力
4. "及时清理"的正确打开方式
不需要靠"清缓存"来保证更新，而是让旧缓存自然失效：

版本号/指纹：资源内容变了就换 URL（上面第②点），这是最干净的更新手段
主动清理：CDN 控制台提供 purge/刷新接口，发版后定向清除即可
缓存分层：浏览器缓存（快、本地）+ CDN 缓存（快、边缘）+ 服务端缓存（回源次数少），配合 Cache-Control: s-maxage 区分层级的缓存时长

修改文件：backend/app.py 与 backend/app_pa.py（线上 wsgi.py 引用 app_pa，两处同步）

落地后的实际策略（已用测试客户端逐条验证）：

  资源类型                    Cache-Control 响应头                        效果
  ---------------------------------------------------------------------------------
  HTML 页面(/、/admin、*.html)  no-cache + ETag/Last-Modified              每次校验，未变返回 304
  CSS/JS 带版本号(?v=xxx)       public, max-age=31536000, immutable        一年强缓存，换版本号即更新
  CSS/JS 未带版本号              no-cache（自动降级兜底）                   防止改文件忘加版本号导致旧缓存
  图片(jpg/png/gif/svg/字体)    public, max-age=2592000（30天）            不常变，长缓存减少重复下载
  API(/api/*)                   no-store                                  数据永远最新
  404/错误响应                   不加缓存头                                避免"加载失败"被缓存

★ 发版须知（重要）：
  1. 修改 CSS/JS 后，必须同步改 HTML 里的版本号，例如 CSS.css?v=20260817c
     → CSS.css?v=20260818a。版本号变了浏览器才会请求新文件。
  2. HTML 内容修改无需任何操作：no-cache 每次都会向服务器校验，改完即生效。
  3. 图片被替换但文件名不变时，用户端最长 30 天后自动更新；
     如需立即生效可换新文件名（产品图本来就带时间戳，天然满足）。

验证结论：
  - /index.html 带 If-None-Match 重请求返回 304（0 字节），协商缓存生效
  - CSS/JS 带版本号均返回 1 年 immutable 强缓存
  - 图片返回 30 天强缓存；API 返回 no-store；404 无缓存头

✅ 二次升级（2026-08-18）—— 升级为"并发式缓存"SWR + 首屏预加载
-----------------------------------------------
1) 图片/字体升级为 SWR（Stale-While-Revalidate，过期后台重新验证）：
    修改：backend/app.py 与 backend/app_pa.py 图片分支
    响应头：public, max-age=2592000, stale-while-revalidate=86400
    含义：30 天内直接命中缓存秒开；过期后 1 天内先用旧缓存立即响应，
          同时后台并发向服务器拉新版本更新缓存——用户永远不等待。
          这是 Next.js / Chrome / 主流 CDN 都在用的最新缓存模式。
    兼容：Chrome 68+ / Firefox / Safari 17+ 支持；旧浏览器自动忽略 SWR
          指令，退化为普通 30 天缓存，无副作用。
2) 首屏 CSS 预加载（index.html）：
    新增 <link rel="preload"> 预加载 CSS.css / header.css / hero.css，
    浏览器在解析到样式表之前就并行下载，缩短首屏渲染等待。
    注意：改版本号时 preload 的 href 必须与 link 完全一致。
3) 哪些还没做（部署层/可选，需要另行操作）：
    - HTTP/2/3 多路复用：waitress 只支持 HTTP/1.1，需换服务器或用 CDN
    - CDN 边缘缓存 + HTTP/3：可将域名接入 Cloudflare 免费版（PythonAnywhere
      支持绑定，需在 Cloudflare 操作 DNS，代码层无需改动）
    - Service Worker 离线缓存：属 PWA 级方案，收益对小站有限且有更新
      风险，暂不建议
